# Galactic Sting

*(internal CMake target / build folders are still named `FractalAdditive` — that is just the
code name and does not affect the product.)*

An MPE-compatible synthesizer (VST3 + Standalone), built
with JUCE. It builds a timbre from a bank of sine partials whose ratios and amplitudes are
generated by a small "spectrum compiler", with deep control over the overtone structure, 
microtuning (MTS-ESP + Scala), generation on scales based on the sensory dissonance curve
of the spectrum, and a mode that turns a Scala scale into the *timbre*
itself.

Target host: **Ableton Live 12** on Windows. Runs standalone too.

---

## Features

**Harmonic engine**
- Sum-of-sines additive voice with a shared, off-thread-compiled partial template.
- **Base harmonic shift N** — the played note becomes harmonic N of an implied fundamental
  (two modes: *Transposed down* = lowest partial on the played pitch, denser as N rises;
  *Original* = natural positions, brighter as N rises).
- **Selection**: all / even / odd / prime harmonics.
- **Prime control**: prime-*limit* (drop harmonics whose largest prime factor exceeds P) or a
  prime *whitelist* (tick the individual primes 2…23).
- **Decay slope**: amplitude roll-off (0 = flat/bright, 1 = saw, 2 = triangle).
- **Fractal** level 1–4: multiplicative self-convolution of the spectrum (self-similar,
  genuinely inharmonic; partial count is monotonic in the level).
- **Phase**: Aligned (coherent pulse, never clips) or Scattered (louder, noisier).

**Per voice**: resonant low-pass filter + filter envelope, amplitude envelope, master gain,
per-voice Nyquist culling and RMS normalisation (no silent partial dropping, no clipping).

**Microtuning** (the `Tuning (scale)` box)
- **12-TET**, **MTS-ESP** (follows a connected ODDSound master; falls back to 12-TET if none),
  or **Scala `.scl`** files. 1/1 is anchored to middle C, so a 12-TET `.scl` reproduces A=440.
- MPE per-note pitch bend rides on top of whatever tuning is active.

**Scala-as-timbre** (the `Timbre (.scl)` box)
- Load a *second*, independent `.scl` whose intervals become the **partials** of the timbre,
  stacked over N periods (`Reps`); `Decay Slope` thins the highs and `Fractal` still applies.
- While active, the harmonic-engine controls are reset to default and greyed out.

**UI**: a colour "scale keyboard" (one cell per key, coloured red→violet by scale degree,
numbered 0…D-1 and resetting each period), a live partial-count meter, and a tuning status line.

## Build

JUCE 8.0.14 is fetched automatically on the first configure (no separate install). You need
**CMake ≥ 3.22** and a C++17 compiler.

### Windows (Visual Studio 2022)

```powershell
# from the repo root
powershell -ExecutionPolicy Bypass -File build.ps1            # Debug
powershell -ExecutionPolicy Bypass -File build.ps1 -Config Release
```

…or drive CMake directly (multi-config VS generator):

```powershell
cmake -B build
cmake --build build --config Release
```

The first configure downloads JUCE (a few minutes); later builds are incremental.

### macOS / Linux

```bash
cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
```

On macOS this produces a VST3 (and can produce AU with a small CMake tweak). Distribution on
macOS additionally needs code-signing / notarisation.

### Outputs

- **Standalone:** `build/FractalAdditive_artefacts/Release/Standalone/Galactic Sting.exe`
- **VST3:** `build/FractalAdditive_artefacts/Release/VST3/Galactic Sting.vst3`

To use in Ableton: copy the `.vst3` to `C:\Program Files\Common Files\VST3\` (Windows) or
`~/Library/Audio/Plug-Ins/VST3/` (macOS), then rescan plug-ins.

## Play it

Click the colour bar with the mouse, or type on the computer keyboard (Ableton "musical
typing" layout):

```
White keys:  A S D F G H J K  ->  C D E F G A B C
Black keys:   W E   T Y U      ->   C# D#  F# G# A#
Z / X      :  shift down / up by one scale PERIOD (12 keys in 12-TET, 19 in 19-EDO, …)
```

3-note+ chords on a PC keyboard depend on the keyboard's n-key rollover (hardware); use a
MIDI controller for full polyphony. Example scales are in [`scales/`](scales/).

## Tests / verification

The DSP is covered by standalone test/verification executables (all exit 0 on success):

```powershell
cmake --build build --config Release --target SpectrumTests TuningTests FftVerify
build/Debug/SpectrumTests.exe        # spectrum-compiler math (harmonic + Scala-timbre)
build/Release/TuningTests.exe        # .scl parsing + note->frequency mapping
build/FftVerify_artefacts/Release/FftVerify.exe   # renders audio, FFTs it, proves no
                                                  # audible partial is dropped / no clipping
```

## Code map (for reading / debugging)

```
CMakeLists.txt                 targets: the plugin, SpectrumTests, TuningTests, FftVerify
source/
  PluginProcessor.{h,cpp}      AudioProcessor: params (APVTS), spectrum-rebuild timer,
                               tuning + Scala-timbre wiring, state save/load
  PluginEditor.{h,cpp}         the whole UI + computer-keyboard input
  ScaleKeyboard.h              the colour scale-degree keyboard component
  dsp/
    Spectrum.{h,cpp}           PURE C++ (no JUCE) "spectrum compiler": harmonic engine +
                               Scala-as-timbre engine -> a list of (ratio, amplitude) partials
    SpectrumEngine.h           off-thread compile + lock-free handoff to the audio thread
    AdditiveVoice.h            the per-voice sine-bank renderer (reads the live template)
    TuningManager.h            12-TET / MTS-ESP / Scala note->Hz (RT-safe) + .scl parser
    SineTable.h                shared sine lookup table
third_party/MTS-ESP/           ODDSound MTS-ESP client (libMTSClient)
tests/  tools/  scales/        unit tests, the FFT verifier, example .scl files
```

**Where to start reading:** `dsp/Spectrum.cpp` (the timbre generation), then
`dsp/AdditiveVoice.h` (how partials become audio), then `PluginProcessor.cpp` (how the UI
parameters drive a rebuild). `SpectrumTests.cpp` doubles as executable documentation of the
spectral math.

## Collaborating on this repo (GitHub)

New to Git? The everyday loop is: **Pull → change → Commit → Push.**

- **Pull** (GitHub Desktop: *Fetch origin* then *Pull*) before you start, to get others' latest work.
- **Commit** your change with a short message describing *what* and *why*.
- **Push** (*Push origin*) to share it.
- If two people changed the **same lines**, Git flags a *merge conflict*; GitHub Desktop walks you
  through picking which version wins. Committing often + pulling before you start keeps these rare.
- Prefer small, focused commits over one giant one — they are far easier to review and to undo.

For bigger or riskier changes, work on a **branch** (GitHub Desktop: *Current branch → New branch*),
push it, and open a **Pull Request** on github.com so a friend can review before it merges into `main`.
